## 目标与范围

* 在现有物品/商店/配方基础上，落地出售（玩家→商店）、合成（配方）、装备位（穿戴/卸下）、耐久（使用与战斗消耗）、品质词条（随机或固定）。

* 保持数据驱动与可后台编辑，统一通过 `adjust_value` 接口变更数值；与事件系统完美对齐，可从命令/事件触发。

## 数据库与配置

* 表新增（在 `schema.sql`，WAL/外键ON）：

  * `user_equipment(user_id, slot, item_id, durability, quality_json, equipped_at)`：记录穿戴与耐久；`slot` 约束由配置定义（如 head/weapon/armor/accessory）。

  * `item_affix_catalog(id, name, type, value_min, value_max, weight, applies_to_category)`：词条库；可后台维护。

  * 扩展 `items.properties` 键：`{durability_max, equip_slot, quality_tier, base_stats}`；扩展索引按需添加。

* 系统参数：

  * `equip_slots`（映射：slot→中文名/可装备类别）、`durability_rules`（使用/战斗扣减系数）、`quality_rules`（随机词条数量与权重）。

## 后台管理 API

* 新增/增强：

  * `admin/api/affixes.py`：词条库 CRUD、导入/导出。

  * 扩展 `items` API 校验：`equip_slot` 与 `durability_max` 合法性、词条模板提示。

  * 玩家视图：`admin/api/inventory.py`（只读，分页查看某用户库存与装备）。

## 运行态 API（core/api/items\_ext.py）

* 出售：`sell_item(user_id, item_id, count, price_gold)` → 加灵石、减物品；支持事件/命令与商店回收策略（按 `shops.pricing_rule_json`）。

* 合成：`craft(user_id, recipe_id)` → 检查材料与成本，减材料与灵石，出成品（可生成品质与词条）。

* 装备：`equip_item(user_id, item_id)` → 检查槽位与类别；写入 `user_equipment`；应用 `base_stats` 或 Buff（通过事件效果或直接属性加成）。

* 卸下：`unequip_item(user_id, slot)` → 回到背包；移除加成。

* 耐久：

  * `apply_durability(user_id, item_id, delta)`：统一接口，正负表示增减；为使用/战斗钩子预留。

  * 当耐久降至 0，触发破损提示与不可装备状态（可配置是否可修复）。

* 品质/词条：

  * `roll_quality_affixes(item_id, quality_tier)`：依据 `quality_rules` 与 `item_affix_catalog` 生成词条集，写入 `quality_json`。

* 所有增减统一走 `adjust_value`；日志语境遵循修真世界观。

## 事件节点

* 效果：

  * `sell_item`、`craft_item`、`equip_item`、`unequip_item`、`apply_durability`。

* 条件：

  * `has_equip_slot_free(slot)`、`durability_gte(item_id, value)`、`has_affix(type)`（可选）。

* 触发器：复用命令触发；前后端复用 `GenericApiEffect` 可直接调用新API。

## 前端页面增强

* 物品管理：

  * 增加装备位/耐久/品质字段编辑；“使用效果”与“基础属性”分区；词条列表预览。

* 商店管理：

  * 增加回收策略（固定价/折扣/分类系数）。

* 配方管理：

  * 增加成本（灵石/时间/耐久消耗/额外材料）编辑器；支持多产出。

* 词条管理：

  * 新增页面维护 `item_affix_catalog`，支持权重与适用类别。

* 玩家视图：

  * 查看指定用户的装备与耐久、词条详情（只读）。

## 命令注册（主文件仅注册）

* `/出售 物品名 [数量] [价格]` → 委托到 `sell_item`（或商店回收策略）。

* `/炼制 配方名` → 委托到 `craft`。

* `/装备 物品名`、`/卸下 槽位` → 委托到 equip/unequip。

* `/修复 物品名`（可选）→ 恢复耐久，消耗灵石/材料。

## 规则与文案

* 提示示例：

  * “你将【玄铁剑】出手，换得【50】灵石。”

  * “你炼成【凝神丹】×1，丹香袅袅。”

  * “你佩戴【青玉佩】于【饰品位】，心境更稳。”

  * “【破损】——你的【玄铁剑】已损至 0/100，不可再战。”

## 验证与联动

* 事件驱动：合成/装备/出售发布到总线（`publish`），任务系统可订阅推进目标（如“合成X次”、“穿戴某品质”）。

* 测试用例：

  * 后台创建配方与词条，命令触发验证扣减与产出，装备加成与耐久扣减，出售结算；查看后台玩家视图与日志。

# 主要框架优化

现在是编辑的JSON内容在后台太难编辑了,都是ID数字,根本不知道是什么东西,不方便编辑,比如新增个配方,需要的材料都是要填写其他材料ID,这样子很难去编辑

## 交付顺序

1. 数据表与系统参数 → 运行态API → 事件效果/条件 → 后台API → 前端页面 → 命令注册 → 示例数据与验证。

如确认，我将按上述顺序开始落地实现并保持与现有架构一致，所有增减统一用 `adjust_value`，提示语为修真语境。
